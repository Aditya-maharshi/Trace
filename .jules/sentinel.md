## 2024-05-24 - [CRITICAL] Prevent IDOR and RLS Bypass in Admin-Backed Helper Functions
**Vulnerability:** A `GET /api/cases/[id]/evidence` route fell back to using `getSupabaseAdmin()` (bypassing Row Level Security) and did not explicitly verify if the user had access to the requested case ID. A `POST` route used an admin-backed helper function (`pinEvidence`) without verifying user authorization to modify the case.
**Learning:** In a codebase where some helper functions (`pinEvidence`, `transitionCase`, etc.) might intentionally use `getSupabaseAdmin()` for atomic updates or system-level actions, the surrounding API route handler *must* enforce strict authorization checks (like `assertCaseAccess`) before calling these functions or querying data. Never assume the presence of `getSupabaseUserClient` handles all security if a fallback to admin is present or if admin helpers are called.
**Prevention:** Always explicitly fetch the object in question and validate authorization (e.g., `assertCaseAccess(details.case, userId)`) within the API route handler before returning data or calling mutation helpers that run with elevated privileges. Never use `getSupabaseAdmin()` as a fallback for user-driven actions in API routes.
