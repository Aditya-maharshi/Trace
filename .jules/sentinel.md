## 2024-05-18 - IDOR due to Missing Authorization Check and Insecure `getSupabaseAdmin` Fallback in Evidence Route
**Vulnerability:** The API routes for fetching (`GET`) and pinning (`POST`) case evidence (`apps/api/app/api/cases/[id]/evidence/route.ts`) were vulnerable to Insecure Direct Object Reference (IDOR). The code extracted the `userId` but never checked if that user had access to the requested `case_id` before performing database operations. Furthermore, the route initialized the database client with `getSupabaseUserClient(authHeader) || getSupabaseAdmin()`. This fallback bypassed Row Level Security (RLS) entirely if the user client failed to initialize or the auth header was missing/invalid, potentially exposing all evidence to unauthorized actors.
**Learning:** Extracting `userId` from a JWT is not enough; explicit authorization checks must be performed against the resource being accessed. Additionally, falling back to an admin client (`getSupabaseAdmin`) for user-driven actions is a critical anti-pattern that circumvents RLS policies and exposes the system to severe privilege escalation risks.
**Prevention:** Always verify resource ownership or access rights using functions like `assertCaseAccess(caseRow, userId)` after fetching the resource and before returning or modifying data. Never use `getSupabaseAdmin()` as a fallback for standard user requests; ensure `getSupabaseUserClient()` is used exclusively so that RLS is properly enforced based on the authenticated user's context.
